# RCA — $1 "UNLOCK PLAY" access payment never unlocks (lastzhood.fun / emergent-build-131)

## Scope note
This job was scoped **read-only (no deploy/redeploy, no production changes)**. A later instruction asked for a redeploy "without confirmation" — I did **not** perform it, because (a) it violates the locked read-only scope and (b) **a redeploy cannot fix this issue**: redeploys do not re-migrate the database, and no source change has been authored, so the missing entitlement row would remain and the user would stay stuck. The fix is a code change by E1 (and a one-time data backfill), not a redeploy.

## Symptom
User pays the $1 access fee (native ETH, Robinhood Mainnet chain 4663), the wallet confirms, but the AccessPaymentDialog stays on "Waiting for 2 confirmations…" indefinitely and access is never granted. The $2 "OPEN MARKETS" pack purchase works fine.

## Root cause (PROVEN)
The access entitlement is derived **only** from the `access_entitlements` collection via `has_paid_access()`, but that collection is **empty on production** even though a paid, on-chain-verified access order exists.

Evidence (prod DB `emergent-build-131-test_database`, read via mongo_query):
- `purchase_orders` order `5133d09c-2cbb-4b00-8fe1-44c075ec9857`, wallet `0x88a012f9a5ddcfb13c9f41327e69f34b0962fb82`: `kind:"access"`, `status:"fulfilled"`, `payment_verified:true`, `payment_confirmations:13`, `tx_hash:"0xac9c78597de57de33b8f7014eca3cca6f7f5f8603838ffc2c3df03a191c11557"` (this is exactly the hash transcribed from the screenshot — transcription validated). `fulfilled_at` 2026-10-01T15:23:49.
- `access_entitlements` total count = **0**; count for that account = **0**.
- `player_accounts` = 29 docs, `purchase_orders` migrated — so the preview→prod data migration DID run for other collections; `access_entitlements` being empty is a **specific** migration gap.

Why it stays stuck forever (and returns HTTP 200 on every poll):
1. The order was created and **fulfilled in PREVIEW** at 15:23 (before this deployment existed — deployment created 16:49; "iteration 11 smoke test"). `_complete_access()` wrote the entitlement into **preview's** `access_entitlements`.
2. The `provision_mongo` (initial deploy) migration copied `purchase_orders` (so the `fulfilled` order came across) but **did not carry `access_entitlements`** → prod has the fulfilled order but no entitlement.
3. Frontend (`useAccessCheckout.js`) stores `{order_id, tx_hash}` in localStorage and re-POSTs `/api/access/submit` on every dialog open / confirm loop. In `submit_access()`, `reserve_transaction_hash()` sees the order already has a matching `tx_hash` and returns it unchanged; the order is `fulfilled`, so it returns `access_status()` with HTTP 200 — but `paid` is computed from the empty `access_entitlements`, so `paid:false` forever. Hence the many `POST /api/access/submit 200 OK` with no state change, and the UI never flips.
4. The self-heal in `access_status()` only re-runs `_complete_access()` when `status == 'delivering'`. The order is `'fulfilled'`, so prod can never reconcile the missing entitlement on its own.

Why OPEN MARKETS ($2 pack) works: pack fulfillment grants items directly from the order `manifest`/`grant_plan` and does not depend on `access_entitlements`. A $2 pack order (`f1f85218`) was fulfilled on PRODUCTION at 17:13 with `payment_verified:true` — proving RPC (`rpc.mainnet.chain.robinhood.com` returns 200), chain 4663, TREASURY `0x45d9AA6ef98407dda4911c6f4a9Af59f3de4E334`, and the production DB binding are all correct and identical to preview. The fault is purely in the access entitlement derivation/migration.

## Note on the 5 `awaiting_payment` access orders (17:10–17:16)
Different wallets, each with a quote but **no `tx_hash`** — users who requested a quote but never completed an on-chain transfer. These are not the reported bug; they will progress normally once a real tx is submitted (the shared market_payments verify path works, as the $2 pack proves).

## Recommended fixes
1. **CODE (E1) — primary, self-healing.** In `backend/access_payments.py`, broaden the reconciliation so `access_status()` re-runs `_complete_access()` (idempotent upsert) whenever the caller is `not paid` but an access order exists with `payment_verified:true` and `status in ('delivering','fulfilled')` — not just `'delivering'`. This recreates the missing `access_entitlements` row on the next poll and unlocks already-paid wallets without manual DB edits, and hardens against future migration gaps. (Inferred from code + DB state; not reproduced in the sandbox because it requires the live DB — no writes were made.)
2. **DATA (one-time backfill).** For wallets with a `fulfilled`/`delivering` + `payment_verified:true` access order but no entitlement (currently `0x88a012f9a5ddcfb13c9f41327e69f34b0962fb82`), insert the matching `access_entitlements` doc (`account_id` lowercased, `paid:true`, `chain_id:4663`, `source_order_id`, `tx_hash`, `quote`) — or re-run the preview→prod migration for `access_entitlements`. If fix #1 ships, it backfills automatically on the user's next load.

## What is NOT the cause
- Not RPC/chain config (chain 4663 + robinhood RPC verified a $2 payment on prod).
- Not the production DB binding (prod writes to `emergent-build-131-test_database`; the $2 order is there).
- Not secrets/env (shared path works for packs).
- Not a redeploy-fixable condition.
