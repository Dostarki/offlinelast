# RCA — lastzhood.fun "Waiting for 2 confirmations" / payment not granting access

## Problem statement
User (wallet `0x88a012f9a5ddcfb13c9f41327e69f34b0962fb82`) completed an on-chain $1 access payment (tx `0xac9c78597de57de33b8f7014eca3cca6f7f5f8603838ffc2c3df03a191c11557`, chain 4663, 13 confirmations) that is already recorded as a **fulfilled, payment_verified** order, yet the app loops on "Waiting for 2 confirmations…" and never grants access. A code fix was authored and tested (iteration_12: 11/11 PASS), deployment notifications arrived, but the user is still stuck.

## Verdict
**The authored fix is NOT in the running production image.** The live image was never rebuilt from the fixed source. The deploys that fired after the fix were `secret_reuse` runs that reuse the OLD image byte-for-byte — no `build_image` ran. The app is still running pre-fix code that has no recovery path for an entitlement that is missing while the order is already `fulfilled`.

## Evidence

### 1. Only one image build exists post-init; the fix-era deploys did NOT rebuild
- Active run `c0321184` (2026-10-01 17:25, type **secret_reuse**, trigger secret_change): `build` step `started_at == completed_at == 17:25:37` → instantaneous, **no rebuild**. Image sha `…2c2e6d362f22…`.
- Run `423ca157` (17:23, secret_reuse): same image sha `…2c2e6d…`.
- Run `57f56ee0` (17:02→17:10, type redeploy): `build` ran 17:02:11→17:09:16 and **produced** image `…2c2e6d…` (build log: `exporting manifest list sha256:2c2e6d362f22…`, pushed tag `57f56ee0…` and `:latest`).
- Initial run `26326437` built a different sha `…557dcfe9…`.

Conclusion: the live image `…2c2e6d…` was frozen at **17:09 on 2026-10-01**. Every deploy after that reused it; no source was rebuilt.

### 2. The running image's source lacks the fix (verified in eph sandbox on run 57f56ee0, which built the live image)
`backend/access_payments.py` in the image:
```python
async def has_paid_access(db, account_id):
    return bool(await db.access_entitlements.find_one(
        {'account_id': account_id.lower(), 'paid': True, 'chain_id': CHAIN_ID}, {'_id': 0, 'account_id': 1}))
```
- `has_paid_access` reads **only** `access_entitlements` — **no recovery** from a verified fulfilled/delivering order.
- `access_status` only auto-completes when `order.status == 'delivering'` AND `payment_verified`. For a `fulfilled` order it does NOT re-complete, so a missing entitlement is never backfilled.
- `submit_access`: when the order is already `fulfilled` it returns `access_status(...)` → `paid:false` (entitlement missing) → client stays on "Waiting for confirmations".
- `grep "recover"` → no match. `backend/player_accounts.py` `grep access_entitlements|backup|export|import|collections` → **empty**.

This is the PRE-FIX code. The authored fix (`has_paid_access` recovers from same-wallet chain-4663 verified delivering/fulfilled order; `_complete_access` preserves dates; `access_status` reads paid before order; `player_accounts.py` backup includes `access_entitlements`) is **absent** from the image.

### 3. Database state matches the pre-fix bug exactly
`purchase_orders` for tx `0xac9c78…`:
- `order_id 5133d09c-2cbb-4b00-8fe1-44c075ec9857`, `access_wallet/account_id 0x88a012…`, `kind access`, `status "fulfilled"`, `payment_verified true`, `payment_confirmations 13`, `fulfilled_at 2026-10-01T15:23:49Z` (fulfilled in PREVIEW, before the 16:49 initial deploy).

`access_entitlements` (4 docs total): `0x41c17f…`, `0x2fee65…`, `0xa0909f…`, `0x4c7eb0…`, all `confirmed_at` 17:21–17:28 (fresh live payers). **No document for `0x88a012…`.**

So: order is fulfilled+verified, but the matching entitlement does not exist in prod. The migration at initial deploy carried `purchase_orders` but the entitlement for this wallet was not present in prod (prior RCA: prod entitlements empty at that time) — exactly what the authored `player_accounts.py` backup-includes-`access_entitlements` change targets. The running code has no way to self-heal this, so the user is permanently blocked.

### 4. API logs confirm the live symptom (active run)
Repeated `POST /api/access/submit → 200 OK` (×16, ×6, ×4 …) with `GET /api/access → 200`. No 5xx. The submit is accepted every time but returns `paid:false` because the entitlement is missing and the code can't recover it — the UI therefore loops.

### 5. Domain routing is correct (ruled out)
`list_domains`: `lastzhood.fun` and `www.lastzhood.fun` both `verified:true`, `ssl_status:active`, provider cloudflare, attached to THIS deployment (`emergent-build-131`). Not routed to a different/previous app.

## Root cause
Two layers, both already fixed in source but **unpublished**:
1. **Image-publish gap (primary/blocking):** The fixed source was never built into a production image. The only post-init build (`57f56ee0`, image `2c2e6d`, 17:09 2026-10-01) predates the fix; subsequent "deployments" were `secret_reuse` runs that reuse that same old image. Production is running pre-fix code.
2. **Underlying data+code bug the fix addresses:** wallet `0x88a012…` has a `fulfilled`/`payment_verified` order but no `access_entitlements` doc (lost at preview→prod migration because the backup export did not include `access_entitlements`); pre-fix `has_paid_access` only reads entitlements with no recovery, so it reports `paid:false` forever.

## Remediation (requires approval — not performed)
1. **Publish the current source** via a FULL redeploy that re-pulls source and runs `build_image` (a normal Redeploy/Deploy). Do NOT use a secret-change/`secret_reuse` deploy and do NOT rollback/redeploy the existing image `…2c2e6d…` — those will NOT contain the fix. Confirm success by checking the new run's image sha differs from `…2c2e6d…` and that its `build` step actually ran (duration > 0).
2. After the rebuilt image is live, wallet `0x88a012…` should self-heal on its next `/api/access` call via the new `has_paid_access` recovery path (recovers entitlement from the same-wallet verified fulfilled order). No manual DB write or fund action is needed if the authored recovery behaves as tested. Verify by querying `access_entitlements` for `0x88a012…` after the user retries.

## Not the cause / explicitly ruled out
- Not a domain/SSL/routing problem. Not a tier/OOM/crash problem (no 5xx, pods healthy). Not a secret problem. Not the deploy pipeline failing — every run shows `success`; the issue is the deploy TYPE (image reuse) not carrying new code.

## Confidence / limits
- Image-does-not-contain-fix: **verified** by reading the exact source that produced the live image sha, plus build/step timestamps and shared image sha across runs.
- Fix correctness itself: **not independently reproduced** here (no prod secrets/live chain in sandbox); relies on the authored change + iteration_12 11/11 report.
